# VoiceVector — Voice & Pilot Pipeline Spec

> Controller speaks (PTT) → transcript → parsed clearance → right pilot → error policy → sim + varied spoken readback → corrections handled.
> Goal: **sub-second machine latency**, with realism delay layered on top. Every number here is an estimate from vendor figures — **measure and display the real ones**.

Companion to `VOICEVECTOR_PLAN_V2.md`. Owners: **B** (voice, parser, TTS), **Tudor** (pilot logic, errors, sim hooks, phraseology sign-off).

---

## 1. Targets

| Metric | Target |
|---|---|
| PTT release → first pilot audio (standard phraseology, machine time) | **≤ 0.8 s** (p50), ≤ 1.2 s (p90) |
| Same, when LLM fallback needed | ≤ 2.0 s (p90) |
| Perceived reply time (incl. deliberate pilot delay) | 1.0–2.5 s, persona-dependent |
| Parser accuracy on golden set | ≥ 90% exact-match `Transmission` |
| Readbacks containing an unplanned error | **0** (validator-enforced) |

Key insight: the machine path is *faster than a real pilot*. We **hide remaining latency inside a deliberate reaction delay**: TTS starts immediately, playback starts at `max(audio_ready, reaction_delay)`.

## 2. End-to-end sequence (one transmission)

```
t=0.00  PTT down        browser starts streaming 16 kHz PCM → server → Scribe Realtime
        (speaking)      partial transcripts arrive every ~100–200 ms
                        server parses partials speculatively (callsign usually known before PTT up)
t=Tu    PTT up          server sends MANUAL COMMIT to Scribe
Tu+0.25 final text      normalise → parse (regex, ~5 ms) → [LLM fallback only if needed]
Tu+0.27 resolved        pilot identified → decision (comply/unable/query) → error policy
Tu+0.28 plan ready      ReadbackPlan → variant engine → validator → TTS request (streaming)
Tu+0.55 first audio     PCM chunks stream to browser, buffered
Tu+~1.2 playback        at max(first_audio, persona reaction delay) → radio filter → speaker
        readback end    + 0.5–2 s → sim applies (possibly erroneous) flown values
```

## 3. Lowest-latency stack

| Layer | Choice | Latency reason |
|---|---|---|
| Capture | Browser **AudioWorklet**, mono PCM16 @ 16 kHz, **100 ms chunks** | No encoding; small chunks = fast partials |
| Transport | One persistent **binary WebSocket** browser ↔ local FastAPI | No per-request setup; server on same laptop |
| STT | **ElevenLabs Scribe v2 Realtime**, WebSocket, **manual commit** on PTT up, **keyterms** | ~150 ms model latency; transcript nearly done before PTT up |
| Parse | In-process Python grammar (regex + clause segmenter) | ~5 ms; no network |
| Parse fallback | **Claude Haiku 5.5**, tool-call with strict schema, streaming, **prompt-cached** system prompt | Only on misses (~10–20%) |
| Pilot logic + errors | In-process, deterministic, seeded | ~1 ms |
| Reply text | **Template variant engine**; variants **pre-generated by Claude at startup**, validated, cached to disk | LLM-quality variety, zero runtime LLM |
| TTS | **ElevenLabs Flash v2.5**, streaming; reused `httpx.AsyncClient` (HTTP/2 keep-alive); PCM output if plan allows, else `mp3_22050` | ~75 ms model + network; no TLS handshake per call |
| Playback | AudioWorklet ring buffer per transmission → radio filter → mixer | Start on first chunk |
| Hide residual | Persona reaction delay overlaps TTS generation | Perceived latency = realism, not lag |

**Fallbacks (same interfaces):** STT → fal `wizper` (batch on PTT up) → local faster-whisper. TTS → fal-hosted TTS → browser `speechSynthesis`. Input → typed box / tag menus.

### Latency techniques, in order of payoff
1. Stream audio *during* speech (never upload-after-release).
2. Keep connections warm (Scribe WS, TTS HTTP/2 client). If Scribe sessions can't span multiple commits, **open on PTT down** and buffer audio until connected — the handshake overlaps speech.
3. Regex fast path; LLM only on misses.
4. No LLM in reply generation at runtime (pre-generated variant bank).
5. Stream TTS; play on first chunk.
6. Overlap TTS with the deliberate pilot delay.
7. **Speculative execution (stretch):** when partial-transcript parse is complete and stable for 250 ms while PTT is still down, pre-build the reply and pre-request TTS into a buffer; on PTT up, if final parse == speculative parse, use it (else discard). Also launch the LLM fallback speculatively on partials if regex fails. Max one speculative TTS per transmission.
8. Prompt caching on the LLM fallback's long system prompt (schema, callsign list, examples).

## 4. Latency budget & instrumentation

| Stage | Path A (regex) | Path B (LLM fallback) | Path C (speculative hit) |
|---|---|---|---|
| PTT up → committed transcript | 150–350 ms | 150–350 ms | 150–350 ms |
| Parse + decide + build reply | < 20 ms | 400–1,200 ms | ~0 (done) |
| TTS request → first chunk at server | 150–350 ms | 150–350 ms | ~0 (buffered) |
| Server → browser → playback start | 30–80 ms | 30–80 ms | 30–80 ms |
| **Machine total** | **~0.35–0.8 s** | **~0.8–2.0 s** | **~0.2–0.45 s** |

**Instrument every stage.** Each transmission carries timestamps: `t_ptt_down, t_ptt_up, t_final, t_parsed, t_plan, t_tts_req, t_tts_first, t_play`. Server sends them with the radio message; UI shows rolling p50/p90 ("Pilot response: 0.62 s machine / 1.4 s perceived"). That's a slide and a judge Q&A answer.

**Benchmark script:** replay 20 recorded controller WAVs headless through the full pipeline (real APIs), print per-stage p50/p90. Run it after every voice change.

## 5. Stage 1 — PTT capture & frequency manager

- **PTT:** hold Space (or on-screen button). `keydown` → `{type:"ptt", state:"down"}` + start streaming; `keyup` → `{type:"ptt", state:"up"}`.
- **Ignore blips:** transmissions < 300 ms are discarded (accidental key).
- **Frequency manager** (`server/radio/frequency.py`) owns who is transmitting:
  - CTRL keyed → pilots won't start new transmissions; queued replies wait.
  - If a pilot was mid-transmission when CTRL keyed (or vice versa) → **both blocked**: CTRL instruction **not delivered**, pilot audio becomes the heterodyne mix, pilot re-calls in 3–6 s (see v2 §11).
  - **Reply scheduler:** serialises pilot transmissions with 0.3–1.0 s gaps; deliberate overlaps only via error policy/injects.
- **Save raw audio** per transmission (debrief replay + Adaption training data).

## 6. Stage 2 — Speech-to-text + normalisation

### Scribe Realtime setup
- Model `scribe_v2_realtime`, PCM 16 kHz, **manual commit** strategy.
- **Keyterms (max 50, ≤ 20 chars each in realtime):** telephony words of airlines in `traffic.json` (Speedbird, Easy, Wizz Air, Ryanair, Tomjet, Vueling, Alpine, Emirates, Qatari, Turkish, Lufthansa…), active fix names (WILLO, TIMBA, MAY, SFD, BOGNA…), "niner", "QNH", "localiser", "Gatwick", "Director", "Tower", "flight level", "squawk". If keyterms can only be set at connect, pick the static top 50; else refresh as traffic changes.
- Keep partials (for speculation) and the committed final.

### Normaliser (`server/voice/normalise.py`) — runs on partials and final
1. Lowercase, strip punctuation; keep a raw copy.
2. Phonetic/ICAO number words → digits: `zero one two tree/three four fower/four fife/five six seven eight niner/nine`; `thousand`, `hundred`, `decimal`/`point`.
   - "two four zero" → `240`; "four thousand" → `4000`; "flight level eight zero" → `FL80`; "one one niner decimal six" → `119.6`; "one zero one three" → `1013`.
3. Numeric-context homophones: `to/too→two`, `for→four`, `won→one`, `ate→eight` **only between number words**.
4. Joined/split tokens: `speed bird→speedbird`, `wizz air→wizzair`, `easy jet→easy`.
5. Phonetic letters for callsign suffixes/GA regs: `alpha bravo→AB`. Also accept the respellings used for TTS (§11.1: `leema→L`, `keh-beck→Q` …) and spelled RNAV points (`kilo kilo sierra two five→KKS25`, SIM_SPEC §2.1.1).
5a. Navaid station names → idents (`seaford→SFD`, `midhurst→MID`), from `data/spoken_names.json` (done 15 Nov).
6. Runways: "two six left" → `26L`.

## 7. Stage 3 — Parsing

### Output: `Transmission`
```python
class Instruction(BaseModel):
    type: Literal[
      "heading", "turn_by", "altitude", "flight_level", "maintain_level",
      "speed", "speed_cancel", "direct", "hold", "approach_clearance",
      "intercept_localiser", "contact", "squawk", "qnh", "expect",
      "resume_nav", "report", "confirm", "traffic_info"]
    value: float | str | None = None
    turn_dir: Literal["L","R"] | None = None
    verb: Literal["climb","descend","maintain"] | None = None
    constraint: Literal["exact","or_greater","or_less","expedite","when_ready"] | None = None
    approach_type: Literal["ILS","LOC","RNP","VISUAL"] | None = None
    runway: str | None = None                 # "26L"
    fix: str | None = None
    unit: str | None = None                   # "tower", "london"
    condition: dict | None = None             # {"after_fix":"WILLO"} | {"passing_level":"FL100"}
    expect_what: str | None = None            # "ILS 26L", "FL70"
    confidence: float = 1.0

class Transmission(BaseModel):
    receiver: str | None                      # resolved callsign, e.g. "BAW117"
    receiver_confidence: float
    intent: Literal["instruction","readback_correction","say_again_request",
                    "readback_request","confirm_request","broadcast","unknown"]
    instructions: list[Instruction]
    self_corrections: int = 0                 # controller said "correction" mid-transmission
    raw_text: str; norm_text: str
    source: Literal["voice","mouse","typed"]
    ambiguities: list[str] = []
    timings: dict = {}
```

### Instruction taxonomy (what the grammar must cover)
| Type | Example (normalised) | Notes |
|---|---|---|
| heading | `turn left heading 240` / `fly heading 240` | `turn_dir` None if "fly heading" |
| turn_by | `turn left 20 degrees` | relative |
| altitude / flight_level | `descend altitude 4000` / `climb FL90` | `verb`; QNH may follow |
| maintain_level | `maintain FL90` | |
| speed | `reduce 210 knots` / `speed 180 or greater` / `expedite descent` | constraint |
| speed_cancel | `no speed restriction` / `resume normal speed` | |
| direct | `proceed direct WILLO` / `direct TIMBA` | fix must exist |
| hold | `hold at WILLO as published` | |
| approach_clearance | `cleared ILS approach runway 26L` | **type + runway** required |
| intercept_localiser | `turn left heading 290 to intercept the localiser 26L` | heading + LOC intercept only, no GS clearance |
| contact | `contact Gatwick Tower 124.225` | unit + freq |
| squawk | `squawk 4521` / `squawk ident` | |
| qnh | `QNH 1013` | |
| expect | `expect ILS approach runway 26L` | stored, not executed |
| resume_nav | `resume own navigation` / `resume the STAR` | |
| report | `report established` / `report speed` | pilot reports later / now |
| confirm | `confirm cleared level` | pilot states what *it believes* (reveals errors) |
| traffic_info | `traffic 2 o'clock 5 miles opposite direction 1000 ft above` | pilot: "looking" / "traffic in sight" |
| conditional (wrapper) | `after WILLO descend FL70` | `condition` on the inner instruction |

### Algorithm (`server/voice/parser/`)
1. **Intent detection** (before clause parsing):
   - starts (after callsign) with `negative` → `readback_correction`
   - contains `i say again` directed at an aircraft with a pending/recent clearance → `readback_correction` (or execution correction — resolved in §13)
   - `say again` → `say_again_request`; `read back` / `readback incomplete` → `readback_request`; `confirm …` → `confirm_request`; `all stations` → `broadcast`
2. **Callsign extraction** (`callsign.py`): take tokens before the first instruction trigger word; fuzzy-match (rapidfuzz token-set ratio) against **spoken forms of aircraft on the scope only** ("speedbird 117", "easy 45 alpha bravo").
   - ≥ 90 → resolved · 70–90 → resolved but `ambiguities += ["callsign_low_conf"]` · < 70 → unresolved.
   - Also accept callsign at the end of the transmission.
   - Two scope matches within 5 points (e.g. BAW117/BAW171) → `similar_callsign` ambiguity (feeds an error type, §10).
3. **Clause segmentation** on trigger words: `turn fly climb descend maintain reduce increase speed expedite direct proceed hold cleared intercept contact squawk qnh expect resume report confirm traffic after when correction negative`.
4. **Per-clause grammar** → `Instruction` with confidence. Range checks: heading 001–360, FL 010–450, altitude 1,000–20,000, speed 120–350, runway ∈ egkk runways, fix ∈ egkk fixes.
5. **Self-correction** (`… descend 4000, correction, 5000`) → later value overrides earlier same-type clause; `self_corrections += 1` (debrief notes it; legitimate phraseology).
6. **Fallback:** if any clause unparsed, any confidence < 0.8, or callsign unresolved but instructions present → **Claude Haiku tool call** with: the normalised + raw transcript, list of active callsigns (spoken + ICAO), allowed fixes/runways, the schema. Rule in prompt: *fill `ambiguities` rather than guess*. Merge: LLM result replaces only failed parts.
7. **Final validation** against sim state (fix exists, runway exists, values in range).

### Golden set (Tudor writes, 60–100 lines)
Real controller phrasing incl. sloppy/non-standard variants, each with expected `Transmission` JSON. Metric = exact-match rate. Also the held-out eval set for the Adaption fine-tune.

## 8. Stage 4 — Pilot resolution

| Situation | Behaviour |
|---|---|
| Resolved, high confidence | That pilot handles it |
| Low confidence | Pilot of best match replies "Was that for Speedbird one one seven?" (or error policy may make the *wrong* similar-callsign pilot take it) |
| Unresolved, instructions present | Silence (realistic) or one pilot: "Station calling Gatwick, say again your callsign" (50/50, seeded) |
| Broadcast | No readback; all pilots update state (e.g. new ATIS letter) |
| Aircraft not on frequency (handed off) | Silence |

---

## 9. Stage 5 — Pilot decision (before errors)

Per instruction, check against aircraft state + `perf.json`:
- **comply**
- **unable** (min clean speed, > 250 kt below FL100, ceiling, intercept angle > 45°, above GS at capture, descent below MSA without approach clearance) → "Unable [reason], Speedbird one one seven". Unable instructions are **never** error-injected.
- **query** (ambiguity, out-of-range) → "Confirm heading or level, Speedbird one one seven?"
- **report/confirm/traffic** → answer from *believed* state (may include an active error — this is how `confirm cleared level` exposes one).

Store the result as the aircraft's **PendingClearance** (see §14): one `ClearanceElement` per instruction.

## 10. Stage 6 — Error policy (deterministic, not the LLM)

Why code not model: controllable, gradeable, testable, zero latency, scenario-scriptable.

### Inputs
difficulty preset, scenario injects (forced errors at times/callsigns), seeded RNG, per-trainee error profile (later), current active errors.

### Taxonomy
**A. Readback errors** (what the pilot says)
| Kind | Example |
|---|---|
| wrong_value_adjacent | 4000 → 5000; 240 → 250; 210 → 220 |
| digit_transposition | 240 → 204; 1013 → 1031 |
| level_type_confusion | FL80 ↔ 8000 ft |
| turn_direction_swap | left → right |
| runway_side_swap | 26L → 26R |
| omitted_element | speed missing from a 3-element readback |
| wrong_callsign | correct content, wrong callsign at end |
| similar_callsign_takeover | **another** aircraft (BAW171) reads back BAW117's clearance (only when a similar callsign is on frequency) |

**B. Execution errors** (what the aircraft does)
| Kind | Example |
|---|---|
| wrong_turn_direction | reads back "left 120", turns right |
| wrong_value_flown | reads back 4000, levels at 5000 |
| level_bust_overshoot | descends 300 ft through cleared level, then recovers |
| delayed_compliance | starts manoeuvre 15–25 s late |
| ignores_instruction | keeps old clearance (as if not received) |

### Coupling modes
| Mode | Readback | Flown | Realism | Weight |
|---|---|---|---|---|
| `consistent` (misheard) | wrong | same wrong value | most common real case | 50% |
| `readback_only` (slip of tongue) | wrong | correct | | 25% |
| `execution_only` (lapse) | correct | wrong | catchable only on radar | 25% |

### Rates & guards
- Base probability per eligible instruction: easy 5%, medium 10%, busy 15%.
- **Max 1 active error per aircraft, 2 globally.**
- Not on: unable/query responses, MAYDAY aircraft, corrections themselves.
- **Reaction-window guard:** don't inject an execution error that would cause a loss of separation within 30 s (pick another kind or skip) — the trainee must have a fair chance.
- Scenario injects bypass rates but not the reaction-window guard (unless flagged).

### Output: `ErrorPlan`
```python
class ErrorPlan(BaseModel):
    id: str; callsign: str; element_idx: int
    kind: str; mode: Literal["consistent","readback_only","execution_only"]
    intended: Any; readback_value: Any; flown_value: Any
```
Applied by **transforming** the PendingClearance element (`readback_value`, `flown_value`), so downstream stages just render/fly what the element says.

## 11. Stage 7 — Readback generation (variation engine)

### Principle
**Style is free, content is verified.** Runtime uses templates; Claude wrote the templates beforehand.

### ReadbackPlan
```python
class ReadbackPlan(BaseModel):
    callsign: str; persona: str
    elements: list[ClearanceElement]   # uses each element's readback_value (may hold a planned error)
    kind: Literal["full","partial_correction","unable","query","report","say_again","checkin"]
    seed: int
```

### Variant bank (`data/readback_variants.json`)
- Built **once at startup** (cached to disk, so restarts are instant/offline): for each `persona × element type`, ask Claude for ~15 phrasings with slots, e.g. heading:
  - `"left heading {HDG}"`, `"left {HDG}"`, `"turning left {HDG}"`, `"heading {HDG}, left turn"`
  - altitude: `"descend altitude {ALT}"`, `"descending {ALT}"`, `"leaving {CUR} for {ALT}"`
  - approach: `"cleared ILS runway {RWY}"`, `"cleared ILS approach {RWY}"`
- **Validate every template** by filling with random values and re-parsing (§11 validator). Drop failures.
- **Tudor reviews the file** for phraseology legality (non-standard but realistic is fine; incorrect is not — errors come only from the error policy).
- Persona fillers/prefix/suffix banks: crisp airline (none), long-haul (calm "and"), student ("uh", slower), rushed (clipped, drops "altitude").

### Composer
1. Order elements: transmission order 70%, random permutation 30%.
2. Pick a variant per element (never the same variant id as this aircraft's last use).
3. Join with connectors (`", "`, `" and "`, `", then "`).
4. Callsign placement: end 80%, start 15%, both 5%. Partial corrections always include the callsign.
5. Format numbers for speech with the shared `numbers.py` (`240`→"two four zero", `4000`→"four thousand", `FL80`→"flight level eight zero", `9`→"niner", `26L`→"two six left", `119.6`→"one one niner decimal six"). **TTS never sees digits.**

### 11.1 Pronunciation (what the TTS is given)
The display text keeps standard spellings; only the speech text (`tts_text`) uses respellings, so ElevenLabs says words the ICAO way. The validator must map respellings back before re-parsing.
- **ICAO phonetic alphabet** (callsign suffixes, ATIS letter, spelled fixes, registrations): use the ICAO pronunciation. Required fix: **Lima is "LEE-mah", not "LIE-mah"** (TTS respelling "Leema"). Check the rest against the ICAO table and respell where the voice gets it wrong: Alfa "AL-fah", Hotel "hoh-TELL", Juliett "JEW-lee-ett", Papa "pah-PAH", Quebec "keh-BECK", Sierra "see-AIR-rah", Uniform "YOU-nee-form", X-ray "ECKS-ray", Whiskey "WISS-key". (UK RTF keeps "three", "four", "five", "niner"; only "niner" differs from plain English.)
- **Navaids by station name**: SFD "Seaford", MID "Midhurst", GWC "Goodwood", LAM "Lambourne" … also inside procedure names ("Seaford one X-ray"). Source `data/spoken_names.json` (Tudor). Done 15 Nov.
- **Five-letter fixes** are said as written ("Willo", "Timba"); add a respelling to `spoken_names.json` only where the voice mispronounces one.
- **RNAV points with digits** (KKS25): spelled phonetically ("kilo kilo sierra two five").
- **Pronunciation test:** a fixture page or script plays each phonetic letter, navaid and a sample of fixes through the real voice so Tudor can approve by ear.

### Validator (`server/pilot/validator.py`)
Parse the generated readback with the **pilot-phrasing grammar** (readbacks omit verbs like "turn", allow "-ing" forms). Compare element set + values to the plan's `readback_value`s (so planned errors must be present, unplanned ones must not). On mismatch: try next variant → fall back to canonical template. Log validator rejections.

### Optional LLM flavour (off the critical path)
Non-readback chatter only ("Gatwick, Speedbird one one seven, any chance of a shortcut?") generated in the background and queued — never inside a readback.

## 12. Stage 8 — TTS, playback, scheduling

- Voice per aircraft (`voice_id`, generated pool — v2 §13). Emergency calls may use fal Chatterbox with high emotion (v2 addendum).
- **Request immediately** after validation; stream chunks over the server→browser WS tagged `{tx_id, callsign}`.
- Browser holds audio until `max(first_chunk, reaction_delay)`, reaction delay from persona: crisp 0.8–1.2 s, long-haul 1.0–1.5 s, student 1.5–2.5 s, rushed 0.5–0.9 s.
- Reply scheduler (§5) decides actual start (frequency busy → wait).
- **Phrase cache** per voice at voice creation: "say again", "standby", "station calling, say again", "looking", callsign alone. Use only for whole short phrases (no stitching mid-sentence).
- Radio filter + squelch per stream; overlap → heterodyne mixer.

---

## 13. Stage 9 — Sim application

- Apply at **readback end + U(0.5, 2.0) s** (realistic pilot reaction), using each element's **`flown_value`**.
- Execution errors:
  - `wrong_turn_direction` → set `turn_dir` opposite.
  - `wrong_value_flown` → target = flown_value.
  - `level_bust_overshoot` → target = cleared ± 300 ft, then auto-correct to cleared after 20 s if not caught.
  - `delayed_compliance` → apply after 15–25 s.
  - `ignores_instruction` → don't apply.
- Approach clearance → arms LOC/GS capture (v1 §9). Expect → stored on aircraft. Conditional → registered trigger (fix passage / level passing) evaluated each tick.
- Every application emits an `Event` (debrief).

## 14. Corrections & follow-ups

### Data model
```python
class ClearanceElement(BaseModel):
    type: str
    intended_value: Any          # what the controller said
    readback_value: Any          # what the pilot said (may differ: planned error)
    flown_value: Any             # what the aircraft does (may differ)
    status: Literal["active","superseded","corrected"]
    error_id: str | None

class PendingClearance(BaseModel):   # per aircraft, last ~3 clearances
    tx_id: str; t: float
    elements: list[ClearanceElement]

class ErrorRecord(BaseModel):
    id: str; callsign: str; kind: str; mode: str
    intended: Any; readback_value: Any; flown_value: Any
    t_planned: float; t_spoken: float | None; t_caught: float | None
    outcome: Literal["pending","caught","missed","self_resolved"]
    caught_by: Literal["readback_correction","execution_correction","confirm_request"] | None
```

### Error lifecycle
```
PLANNED ─► SPOKEN (readback played) ─┬─► CAUGHT  (controller corrects / confirm reveals it and corrects)
                                     └─► MISSED  (next transmission to this a/c without correction,
                                                  or 30 s elapsed, or consequence occurs)
execution_only: PLANNED ─► EXECUTING ─► CAUGHT / MISSED (60 s, or LoS / level bust consequence)
```

### A. Readback correction (the key flow)
Controller: *"Speedbird one one seven, negative, descend altitude four thousand."*
(or *"…negative, I say again, four thousand"* / *"…negative, left heading two four zero"*)

1. Parser: `intent=readback_correction`, receiver `BAW117`, instructions `[altitude 4000]`. A **value-only** correction ("negative, four thousand") is typed by matching the value's domain against the aircraft's active elements (prefer the element with an active error).
2. Match each corrected instruction to the most recent active `ClearanceElement` of the same type.
3. For each match, compare the controller's value with the pilot's **readback_value / flown_value**:
   - **differs** → this is a corrected element: set `intended = readback = flown = new value`, `status=corrected`; close the `ErrorRecord` as **caught** (`t_caught`, `caught_by`).
   - **same** (pilot was right) → "unnecessary correction" event (minor, debrief).
4. If the controller **repeated the whole clearance**, elements whose values already matched are *not* re-read.
5. **Pilot reads back only the corrected element(s)**, using `kind="partial_correction"` templates:
   - "Four thousand, Speedbird one one seven."
   - "Descend four thousand, sorry about that, Speedbird one one seven."
   - "Correction, altitude four thousand, one one seven… Speedbird one one seven."
   - Validator enforces: only corrected elements + callsign.
   - If nothing actually differed: "Four thousand, Speedbird one one seven" (re-reads what was mentioned).
6. Sim: if the aircraft was already flying the wrong value (`consistent` mode), retarget immediately after the partial readback + reaction delay.
7. A correction that gives a *new different* value (controller changed their mind) is applied as given; debrief notes it.

### B. Execution correction (wrong turn / wrong level on radar)
Controller: *"Speedbird one one seven, I say again, turn LEFT heading one two zero"* or *"…check heading, you appear to be turning right."*
- Intent: correction (I-say-again + same-type element whose **flown_value** differs from intended).
- Pilot: partial readback of the corrected element ("Left heading one two zero, sorry, Speedbird one one seven"); sim reverses turn/retargets; ErrorRecord caught via `execution_correction`.

### C. Confirm request
*"Speedbird one one seven, confirm cleared altitude."* → pilot states **readback_value** ("Cleared five thousand, Speedbird one one seven"). If wrong, the controller then corrects (flow A). ErrorRecord `caught_by=confirm_request` once corrected.

### D. Say again / readback request
- *"Say again"* → pilot repeats last transmission (same text, cached audio if available).
- *"Read back"* / *"readback incomplete"* (after an `omitted_element` error) → pilot re-reads the full clearance including the omitted element; error caught.

### E. Missed errors
On the next transmission to that aircraft (not a correction), or after 30 s (readback errors) / 60 s or a consequence (execution errors): `outcome=missed`; the aircraft keeps flying `flown_value`. Debrief lists it with timestamps and what the correct catch would have been.

### F. Debrief phraseology note
For readback corrections, check the controller used *"negative … I say again …"* (CAP 413 style — **Tudor to confirm wording**) and restated the full correct element. Credit the catch either way; flag phraseology separately.

## 17. Tests

1. **Parser golden set:** exact-match ≥ 90%; per-type confusion matrix.
2. **Validator property test:** for every template × 200 random values: `parse_readback(fill(t, v)) == v`.
3. **Number round-trip:** `to_digits(to_speech(x)) == x` for headings, levels, altitudes, speeds, QNH, squawks, frequencies, runways.
4. **Correction scenarios (scripted):**
   - consistent alt error → "negative, descend altitude 4000" → partial readback contains *only* altitude + callsign; target 4000; ErrorRecord caught.
   - controller repeats full 3-element clearance after a 1-element error → only that element re-read.
   - unnecessary correction → event logged, pilot re-reads mentioned element.
   - execution wrong-turn → "I say again turn left…" → turn reverses; caught.
   - no correction for 30 s → missed; aircraft flies wrong value.
5. **Error guard:** no execution error ever produces LoS within 30 s (run 500 seeded sims).
6. **Latency bench:** 20 WAVs, per-stage p50/p90, fail if path-A p90 > 1.2 s.

## 18. Risks

| Risk | Mitigation |
|---|---|
| STT mishears numbers/callsigns | Keyterms, normaliser, scope-only fuzzy match, "say again" path |
| Scribe session can't span commits | Open on PTT down, buffer until connected |
| LLM fallback spikes latency | Regex coverage from golden set; prompt caching; speculative launch on partials |
| Variant bank produces non-standard phrasing | Validator + Tudor review; canonical fallback template |
| Errors feel unfair | Rate caps, 1 per aircraft, reaction-window guard, seeded demo |
| Correction mis-typed (value-only) | Prefer element with active error; else pilot queries "confirm altitude or speed?" |
| Network at venue | Local fallbacks (faster-whisper, browser TTS), typed input, recorded backup demo |

## 20. Live pipeline trace and benchmarks

### 20.1 Pipeline trace (owner: Sanju, data; Bhavin, panel — not built yet)
Goal: for every transmission, an on-screen waterfall (like browser dev tools) of every stage in milliseconds, so judges see what is actually happening: speech → speech-to-text → parse → sim check → pilot decision → readback → validation → voice → playback. Bars fill in as stages complete. Every number is measured on the server, never estimated.

**Timing.** Stamp every stage with `time.perf_counter_ns()`. Anchor = **PTT up** for a controller transmission, **compose start** for a pilot-initiated call. Speech before PTT up has a negative `t0_ms`.

**Stages — exact names** (the panel keys colours and labels off these):
| name | category | from → to | detail keys |
|---|---|---|---|
| `speech` | capture | PTT down → PTT up | `duration_ms` |
| `stt_partials` | stt | first partial → last partial | `count` |
| `stt_final` | stt | PTT up → committed final text | `provider` ("scribe" \| "fal_wizper" \| "local") |
| `normalise` | language | — | `tokens` |
| `parse` | language | — | `path` ("regex" \| "llm" \| "mixed"), `clauses`, `unparsed` |
| `llm_fallback` | language | only if used | `model`, `ttft_ms` |
| `callsign_match` | language | — | `callsign`, `score` |
| `evaluate` | sim | `world.evaluate()` | `statuses` (e.g. ["OK", "UNABLE"]) |
| `pilot_decision` | pilot | `pilot.handle_transmission()` | `kind`, `error_policy`: "evaluated" — **never reveal a planned error** unless "Reveal errors" is on (then `planned_error_kind`) |
| `compose` | voice | — | `variant_ids`, `persona` |
| `validate` | voice | — | `attempts`, `fallback` (bool) |
| `tts_first_audio` | voice | TTS request → first chunk | `model`, `voice`, `machine_ms` |
| `reaction_hold` | playback | first chunk → release | `persona_delay_ms` |
| `playback` | playback | release → audio end | — |
| `apply_scheduled` | sim | audio end → `schedule_apply` call | `apply_at_sim_s` |

- `total_ms` = anchor → release (first pilot audio heard). `machine_ms` = anchor → first TTS chunk; it must equal the latency chip.
- **When to send** a `TraceMsg` (all clients): **provisional** after `validate` (`final=false`), updated at release, **final** at audio end (`final=true`).
- **Blocked transmission:** one trace with `stt_final` … then a `blocked` stage (category `sim`, status `error`).
- Append every final trace to `runs/<session>/traces.jsonl` (the benchmarks read it). Tracing must fail open: an exception in tracing never interrupts the voice path. No audio and no transcript text in the trace by default.
- **Acceptance:** 20 consecutive transmissions each produce exactly one final trace; no negative durations except `speech`; `machine_ms` matches the latency chip.
- Message shapes: `CONTRACTS.md` §3.1. Panel: `ASSIGNMENT_BHAVIN.md` §11.

### 20.2 Benchmarks

The offline suite should live under `server/tests/voice/bench/` and use fixed, versioned input manifests. Report parser exact accuracy and confusion matrix, STT word error rate, validator/property coverage, phrasing variety, and end-to-end p50/p95/p99. Every result must include sample count, corpus version, model/provider version, hardware, and run conditions. Initial targets are parser ≥95% on 100+ labelled utterances, STT WER ≤10% on 50+ clips, and p95 voice-to-caption ≤1,500 ms on 50+ runs. These are proposed acceptance targets, not measured claims. Preserve the original MVP's latency readout separately; benchmark percentiles must not be inferred from its last 10 samples.
