# Git & collaboration rules — Tudor's agent

You are building **Tudor's part** of SweatboxAI (simulation, pilot logic, rules, data). Three people and three AI agents work in one repo at the same time. These rules keep us from overwriting each other. Follow them exactly.

## 1. What you may edit
```
data/                                   (except readback_variants.json and voices.json, which are Sanju's)
server/sim/
server/rules/
server/pilot/engine.py  decision.py  errors.py  clearance.py
server/tests/sim/  server/tests/pilot/  server/tests/rules/
server/tests/voice/golden_parse.jsonl   (the parser golden set — you write it, Sanju only reads it)
```
**Everything else belongs to someone else.** Never edit it, even to "fix" a bug or make an import work.

| Owner | Their area |
|---|---|
| Sanju | `server/voice/`, `server/agents/`, `server/pilot/readback.py validator.py variants_build.py`, `web/src/audio/`, `server/tests/voice/` (except the golden set), `data/readback_variants.json`, `data/voices.json` |
| Bhavin | everything else: `server/main.py hub.py session.py feed.py`, `server/contracts.py`, `web/src/protocol.ts`, all of `web/` except `web/src/audio/`, `CLAUDE.md`, `README.md`, dependency files |

**If a change outside your area seems needed: STOP and tell Tudor.** He will ask the owner in the group chat. Write down exactly what you need (file, function, why).

## 2. One-time setup
```sh
git clone <repo-url> && cd sweatbox-ai
sh tools/git/install-hook.sh tudor      # blocks commits outside your area
cp .env.example .env                    # keys from Tudor
python -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt
```
Do not add Python or npm dependencies. They're all pre-installed by Bhavin. If something is genuinely missing, tell Tudor.

## 3. Work loop (repeat for every task)
```sh
git checkout main && git pull --rebase origin main
git checkout -b tudor/<short-task>       # e.g. tudor/ils-capture
# ...work, commit small and often...
git add <only your files> && git commit -m "[sim] ILS localiser capture"
pytest server/tests/sim server/tests/pilot server/tests/rules
git pull --rebase origin main            # get others' work, replay yours on top
pytest && python server/tests/integration/smoke_test.py
git checkout main && git merge --ff-only tudor/<short-task> && git push origin main
git branch -d tudor/<short-task>
```
- Merge to `main` at least every 1–2 hours. Never keep a big branch overnight.
- Commit prefixes: `[sim]`, `[pilot]`, `[rules]`, `[data]`.
- Never `git push --force` to `main`. Never commit `.env`, `runs/`, `__pycache__/`.

## 4. Shared files — hands off
- **`server/contracts.py`** defines the interfaces you implement (`WorldAPI`, `PilotAPI`, `RulesAPI`). Implement them **exactly**. Need a new field? Tudor asks Bhavin; only additive optional fields are allowed (CONTRACTS.md §7). Bhavin commits the change and updates `protocol.ts`.
- **`server/session.py`** wires your classes in. Constructor signatures are fixed: `World(bus, data_dir)`, `PilotEngine(world, bus, data_dir)`, `RulesEngine(world, bus, data_dir)`.
- **`data/readback_variants.json`** is generated by Sanju. Tudor reviews it by **sending notes** (variant ids that are wrong), not by editing it.

## 5. If you hit a merge conflict
- Conflict in **your** files: resolve it, re-run the tests.
- Conflict in **anyone else's** file (shouldn't happen): don't hand-merge it. Take main's version (`git checkout --theirs <file>` during a rebase), finish the rebase, and tell Tudor.
- The hook blocks a commit: unstage the listed files (`git restore --staged <file>`), revert your edits to them, and report what you needed.

## 6. Done means
Tests pass, the smoke test passes, your branch is merged into `main`, and `main` still starts (`uvicorn server.main:app`).

## 7. Post-MVP technical-depth ownership
After the end-to-end MVP works, Tudor owns `server/sim/forecast.py`, `server/sim/live_import.py`, and the corresponding simulator tests. Keep Monte Carlo forecasts seeded, bounded, advisory, and separate from deterministic STCA. Imported traffic is normalized into simulated aircraft only; never connect to or transmit control to a live network. Verify provider terms and data-quality assumptions before enabling an import source.
